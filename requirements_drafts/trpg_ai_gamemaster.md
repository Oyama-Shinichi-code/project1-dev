## 1. 概要・コンセプト

LLM（Claude）がゲームマスター（GM）役を務め、プレイヤーの自由入力に応じてストーリーを進行させる、テキストベースのアドベンチャー/TRPGアプリ。

- GUIはシンプル構成（チャット欄＋キャラクターステータス＋インベントリ表示程度）とし、ゲーム進行の複雑さはすべてLLM側のプロンプト・ロジックに委ねる。
- 「新しいシナリオを追加する」こと自体が機能拡張になるよう設計する（シナリオ＝データ、エンジン＝共通コード、という分離を徹底する）。
- 開発者個人の学習目的として、Claude Codeのsub-agent・skill・hookをアプリの内部構造に意図的に対応づけ、これらの機能を実践的に使う練習とする。

### コンセプトの核
1. **拡張性優先** - 新シナリオ・新ルールセットの追加が最小のコード変更で済む。
2. **GMの一貫性** - LLMがGMとして世界観・ルール・キャラクター設定を破らずに進行できるよう、状態管理とプロンプト設計を工夫する。
3. **個人開発での実践しやすさ** - 一人のエンジニアが趣味/学習として継続的に拡張しやすい構造。

## 2. 想定ユーザー・ユースケース

### 想定ユーザー
- テキストアドベンチャー/TRPGが好きなソロプレイヤー（まずは開発者本人が主要ユーザー）。
- 友人同士で一つのPCを囲んで遊ぶ、あるいは画面を共有しながら一人が入力役になる小人数プレイ（将来的な拡張候補）。
- Claude Code自体の学習素材としてこのアプリの開発プロセスを見る、技術的な読者（開発者自身の技術検証用途も含む）。

### 主なユースケース
1. シナリオを選択し、キャラクターを作成（またはプリセットを選択）してゲームを開始する。
2. チャット欄に行動・発言を自由入力し、AI GMからの地の文・NPC発言・判定結果を受け取りながら物語を進める。
3. セッションを中断し、後日続きから再開する（セーブ/ロード）。
4. インベントリやキャラクターシートを確認しながら、戦闘・探索・交渉などのイベントを進行する。
5. （開発者向け）新しいシナリオファイルを追加し、アプリを再起動するだけで新しい物語を遊べるようにする。

## 3. 主要機能

### 3.1 MVP範囲

| 機能 | 内容 |
|---|---|
| チャットUI | プレイヤー入力欄、GM応答表示欄（スクロール可能なログ） |
| AI GM応答生成 | プレイヤー入力とゲーム状態を受け取り、Claude APIで地の文・NPC発言・選択肢を生成 |
| キャラクターシート表示 | 名前・HP・簡易ステータス・簡易スキルを画面に表示（編集は最小限） |
| インベントリ表示 | 所持アイテムのリスト表示（取得/使用/破棄程度の操作） |
| シナリオ選択 | 用意されたシナリオ（1〜2本）から選んでゲーム開始 |
| セーブ/ロード | 進行状況をローカルファイルに保存し、後から再開できる |
| 固定ルールセットでの判定 | サイコロ風の簡易判定（成功/失敗）をLLMまたはローカルロジックで処理 |

### 3.2 MVP後の拡張候補

| 機能 | 内容 |
|---|---|
| 複数シナリオ/キャンペーン管理 | シナリオの追加・切り替え・章構成の管理 |
| キャラクタービルダー | 種族・クラス・能力値などを選んで本格的にキャラ作成 |
| 戦闘専用UI | ターン制戦闘のための補助画面（敵情報、行動選択肢など） |
| マップ/位置情報表示 | テキストベースの簡易マップやロケーション表示 |
| 音声・BGM | シーンに応じたBGM/効果音の再生 |
| マルチプレイ | 複数プレイヤーが同じセッションに参加（別アプリ/Web化も視野） |
| シナリオエディタ | GUI上でシナリオ・クエストを作成できるツール |
| 実績/ログ振り返り | プレイ履歴の要約、ハイライトの自動生成 |
| 画像生成連携 | シーンやキャラクターの挿絵を自動生成 |

## 4. 画面構成・UI要素

GUIフレームワークは **PySide6（Qt for Python）** を想定。

### 4.1 画面構成（MVP）

```
+--------------------------------------------------+
| メニューバー（ファイル / シナリオ選択 / 設定）         |
+------------------------+---------------------------+
|                        |  キャラクターステータス      |
|   チャットログ表示欄     |  （名前・HP・簡易ステータス） |
|   （GM発言・自分の発言）  +---------------------------+
|                        |  インベントリ一覧           |
|                        |  （アイテム名・個数）         |
+------------------------+---------------------------+
| プレイヤー入力欄 [テキストボックス] [送信ボタン]        |
+--------------------------------------------------+
```

### 4.2 主要UI要素
- **チャットログ欄**: GM発言（地の文/NPC台詞）とプレイヤー発言を区別して表示（話者ごとに色分け・アイコン程度）。
- **入力欄**: 自由入力テキストボックス＋送信ボタン（Enterキー送信対応）。
- **キャラクターパネル**: 名前、HP/MP等のステータスバー、簡易スキル一覧。
- **インベントリパネル**: アイテムリスト（アイコンまたはテキストのみ）。
- **シナリオ選択画面**: 起動時またはメニューから、利用可能なシナリオ一覧を表示して選択。
- **セーブ/ロードダイアログ**: 保存スロットの選択、ファイル名入力程度の簡易UI。
- **ステータスバー/ローディング表示**: LLM応答待ちであることを示すインジケータ（重要。LLM応答には数秒〜十数秒かかるため）。

## 5. 技術スタック

| 分野 | 技術 | 補足 |
|---|---|---|
| GUIフレームワーク | PySide6 | Qtベースで高機能かつPythonとの親和性が高い |
| 言語 | Python 3.11+ | 型ヒントを活用し保守性を確保 |
| LLM呼び出し | Anthropic公式SDK（`anthropic`パッケージ） | Messages APIを直接呼び出す構成を基本とし、必要に応じてTool Runner（`client.beta.messages.tool_runner`）でNPC行動やサイコロ判定などのツール呼び出しを自動化する。モデルは既定でClaude Opus系（高品質な物語生成向け）、コスト重視の場面ではSonnet系に切り替え可能な設計とする |
| 非同期処理 | `asyncio` または `QThread` | LLM応答待ちでUIをブロックしないようにする（PySide6のメインスレッドをブロックしない設計が必須） |
| セーブデータ形式 | JSON（ローカルファイル） | 人間が読める形式を優先。将来的にSQLiteへの移行も検討余地あり |
| シナリオ定義形式 | YAMLまたはJSON＋Markdown | ルール・設定はYAML/JSON、GM用のフレーバーテキストや背景説明はMarkdownで管理し、プロンプトに埋め込む |
| 設定管理 | `.env`またはOS標準の設定ディレクトリ | APIキー等の機密情報はGit管理対象外にする |
| パッケージ管理 | `uv`または`poetry` | 依存関係の再現性を確保 |
| テスト | `pytest` | ゲームロジック部分（判定、セーブ/ロード）を中心に単体テスト |

## 6. データ構造

### 6.1 キャラクターデータ（例: JSON）

```json
{
  "character_id": "char_001",
  "name": "アリア",
  "stats": {
    "hp": 20,
    "max_hp": 20,
    "mp": 10,
    "max_mp": 10,
    "strength": 5,
    "intelligence": 7,
    "agility": 6
  },
  "skills": ["ファイアボール", "応急手当"],
  "inventory": [
    {"item_id": "item_potion", "name": "回復薬", "quantity": 3}
  ],
  "flags": {
    "met_npc_elder": true
  }
}
```

### 6.2 シナリオデータ（例: YAML + Markdown）

```yaml
scenario_id: "forest_of_whispers"
title: "囁きの森"
version: "1.0"
starting_location: "forest_entrance"
npcs:
  - npc_id: "elder"
    name: "長老イオ"
    personality: "謎めいた知識人。遠回しに真実を語る"
rules:
  dice: "d20"
  difficulty_default: 12
```

- シナリオ本文・GM向けの背景設定・NPCの台詞方針などはMarkdownファイルで管理し、LLM呼び出し時にシステムプロンプトまたはコンテキストとして注入する。

### 6.3 進行状況（セーブデータ、例: JSON）

```json
{
  "save_id": "save_20261009_01",
  "scenario_id": "forest_of_whispers",
  "current_location": "ancient_shrine",
  "turn_count": 42,
  "character": { "...": "6.1のキャラクターデータ" },
  "chat_history_summary": "プレイヤーは長老から鍵の在処を聞き出し、古代の祠へ向かった。",
  "chat_history_recent": [
    {"role": "user", "content": "長老に鍵のことを尋ねる"},
    {"role": "assistant", "content": "長老は静かに頷き……"}
  ],
  "timestamp": "2026-10-09T10:00:00+09:00"
}
```

- 長い会話履歴をそのままLLMに渡すとコンテキストが肥大化するため、**要約（summary）＋直近の履歴**という二層構造を基本とする。

## 7. Claude Codeのagent/skill/hookの活用案

このアプリ自体の「開発プロセス」でClaude Codeの機能を練習的に使う、という観点での対応案。

| Claude Code機能 | アプリ開発での活用イメージ |
|---|---|
| **sub-agent** | - NPC応答生成専用のsub-agent（キャラクター性を保った台詞のみ生成）<br>- ストーリー分岐・イベント生成専用のsub-agent（プレイヤーの行動から次の展開候補を複数提案）<br>- シナリオ整合性チェック用のsub-agent（新規シナリオ追加時に既存ルールと矛盾がないかレビュー） |
| **skill** | - シナリオ作成テンプレートskill（新シナリオのYAML/Markdown雛形を生成）<br>- クエスト生成テンプレートskill（サブクエストの構造をひな形から作る）<br>- バランス調整skill（敵の強さ・アイテム効果などのパラメータ調整を支援） |
| **hook** | - セーブ処理の自動記録hook（一定ターン数ごと、または重要イベント後に自動セーブをトリガー）<br>- 進行ログの自動記録hook（プレイ履歴をログファイルに自動追記、デバッグ用）<br>- コード変更時の自動テスト実行hook（シナリオファイル追加時にスキーマ検証を自動実行） |

> 注: 上記はアプリ本体の実行時に使う「ゲーム内GM」のロジック（Claude APIを直接呼び出すコード）と、アプリを開発する際にClaude Codeの機能を使う話（開発支援）を分けて捉える必要がある。本アプリの売りである「拡張性」を具体的に体現する最初の一歩として、まずは開発支援側（シナリオ追加のskill化、セーブ処理のhook化）から練習するのが現実的。

## 8. 拡張ロードマップ

1. **MVP** - 1シナリオ、簡易キャラ、チャットUI、セーブ/ロード、簡易判定。
2. **シナリオ追加基盤の整備** - シナリオ定義フォーマットを固め、2本目以降のシナリオを追加しやすくする（シナリオ作成skillの導入）。
3. **キャラクタービルダー** - 能力値・スキル選択などの本格的なキャラクター作成フローを追加。
4. **戦闘システムの強化** - ターン制のUI・判定ロジックを拡充。
5. **マップ/位置情報の可視化** - テキストベースの簡易マップ表示。
6. **シナリオエディタ（GUI）** - 非エンジニアでもシナリオを作成できるツールの提供。
7. **マルチプレイ対応検討** - 複数人プレイへの拡張（アーキテクチャの見直しが必要になる可能性が高い）。
8. **音声/画像など表現力強化** - BGM、挿絵生成などのリッチ化。

## 9. 開発上の懸念点・リスク

- **LLM応答の一貫性維持**: 長時間プレイでの設定忘れ・矛盾（キャラクターの能力値やフラグの逸脱）が発生しやすい。コンテキスト管理（要約＋直近履歴）とシステムプロンプトの設計が肝になる。
- **応答速度とUX**: LLM応答に数秒〜十数秒かかるため、UIがブロックされないような非同期処理が必須。ローディング表示や「考え中」のフィードバックも重要。
- **コスト管理**: Claude APIの呼び出し回数・トークン量に応じて費用が発生する。個人開発では使用量の見積もりとモデル選択（品質とコストのバランス）が必要。
- **不正な/想定外のプレイヤー入力への対応**: 自由入力ゆえにプロンプトインジェクションやルール破りの入力が来る可能性があり、GM側のガードレール設計が必要。
- **シナリオ拡張時の品質保証**: 新シナリオ追加がバグや矛盾を生まないよう、スキーマ検証やレビュー用sub-agentの仕組みを早期に整備する必要がある。
- **セーブデータの後方互換性**: シナリオやキャラクターデータの構造が将来変わった場合、既存セーブデータの移行方法を検討しておく必要がある。
- **一人開発であることのリスク**: レビュー者がいないため、Claude Codeのsub-agent/skill/hookを活用した自己レビュー・自動チェックの仕組みが実質的な品質担保手段になる。
- **スコープ肥大化**: 「拡張性の高さ」が売りであるがゆえに、MVPの段階で機能を広げすぎないよう注意が必要（まずは1シナリオを確実に遊べる状態にすることを優先する）。

---

## 10. まとめ

本アプリは「シンプルなGUI＋高度なLLM駆動のGM」という構成により、UI実装の負担を抑えつつ物語表現の奥行きを確保できる点が強み。また、シナリオ追加＝機能拡張という設計方針により、開発者自身の学習（Claude Codeのagent/skill/hook活用）と両立しやすいテーマである。MVPでは「1シナリオを安定して遊べること」に集中し、拡張性の検証は拡張ロードマップに沿って段階的に行うことを推奨する。
