# ローカルファイル/ノート向けRAGチャットアプリ 要件定義書

## 1. 概要・コンセプト

自分のローカル環境にあるメモやドキュメント（Markdown、PDF、テキストなど）に対して、自然言語で質問できるデスクトップ向けチャットアプリケーション。

LLM（大規模言語モデル）とベクトル検索（RAG: Retrieval-Augmented Generation）を組み合わせ、ユーザーの質問に関連するドキュメントの断片を検索し、それらを根拠としてLLMが回答を生成する。クラウドにデータをアップロードせず、自分のPC内で検索・推論を完結させることを重視する（ローカルLLM利用、またはAPI利用のいずれにも対応できる設計とする）。

このアプリの内部動作（質問を解釈 → 関連情報を検索 → 情報をまとめて回答を生成）は、Claude Code自体のツール呼び出し・検索・要約の仕組みと類似しており、開発者がClaude CodeのSub-agent/Skill/Hook機能を学ぶ実践的な題材としても適している。

## 2. 想定ユーザー・ユースケース

### 想定ユーザー
- 個人開発者・エンジニア（開発者自身を含む）
- 研究者・学生など、大量のメモ・論文・資料を抱える人
- ナレッジワーカー（議事録、仕様書、社内ドキュメントを多く扱う人）

### ユースケース例
- 「先月書いた設計メモの中で、認証方式について何を検討していたか教えて」
- 「このPDFフォルダの中から、〇〇に関する記述がある箇所を一覧にして」
- 「自分の日報・議事録から、〇〇プロジェクトの進捗をまとめて」
- 複数ファイルに分散した情報を、1つの質問で串刺し検索して要約してもらう
- 回答の根拠となった元ドキュメント（出典）を確認し、原文にすぐ飛べる

## 3. 主要機能

### 3.1 MVP範囲

- **ドキュメント登録・インデックス化**
  - 指定フォルダ内のMarkdown / テキスト / PDFファイルを読み込み、チャンク分割してベクトル化しインデックスに保存
  - 手動での「再インデックス」実行ボタン
- **チャットUI**
  - 質問を入力し、LLMからの回答をチャット形式で表示
  - 回答に根拠として使われたドキュメント（出典・該当箇所）を表示
- **ドキュメント管理画面**
  - 登録済みドキュメントの一覧表示（ファイル名、登録日時、インデックス状態）
  - ドキュメントの追加・削除
- **チャット履歴の保存・再読み込み**
  - 会話単位でローカルに保存し、後から見返せる
- **LLM呼び出し設定**
  - APIキー等の設定画面（利用するLLMプロバイダ・モデルを選択）

### 3.2 拡張候補（MVP後）

- フォルダ監視による自動インデックス更新（ファイル追加・変更・削除の検知）
- 複数ノート・複数プロジェクトの切り替え（ワークスペース機能）
- 回答のストリーミング表示
- 検索結果のハイライト表示（元ドキュメント内の該当箇所を強調）
- タグ・フォルダ単位での検索範囲の絞り込み
- 複数LLMプロバイダの切り替え（Claude、ローカルLLM、OpenAI等）
- 画像・画像内テキスト（OCR）への対応
- Office系ファイル（Word、Excel、PowerPoint）への対応
- チャットからドキュメントへの逆リンク（この回答はどのメモから来たか、を起点にメモを開く）
- ドキュメント間の関連性可視化（グラフビュー）
- エクスポート機能（チャットログ、要約結果をMarkdownやPDFで出力）

## 4. 画面構成・UI要素

GUIフレームワークはPySide6（Qt for Python）を想定。

### 4.1 メインウィンドウ構成
- 左サイドバー：チャット履歴一覧（過去の会話を選択して再開）
- 中央：チャット画面
  - メッセージ表示エリア（ユーザー発言／AI回答を区別して表示）
  - 回答下部に出典ドキュメントのリンク・抜粋を表示
  - 質問入力ボックス＋送信ボタン
- 右サイドバー（または別タブ）：ドキュメント管理画面
  - 登録済みドキュメント一覧（テーブル表示：ファイル名、種類、インデックス状態、更新日時）
  - 「フォルダを追加」「ファイルを追加」「再インデックス」「削除」ボタン
  - インデックス処理中の進捗表示（プログレスバー）

### 4.2 その他画面
- 設定画面（モーダルまたは別ウィンドウ）
  - LLMプロバイダ・モデル選択、APIキー入力
  - 埋め込みモデルの選択
  - インデックス対象フォルダの管理
- 初回起動時のセットアップウィザード（任意）

## 5. 技術スタック

| カテゴリ | 候補技術 |
|---|---|
| GUIフレームワーク | PySide6（Qt for Python） |
| 言語 | Python 3.11+ |
| 埋め込みモデル | sentence-transformers（ローカル）、またはOpenAI/Claude系埋め込みAPI |
| ベクトルDB | ChromaDB、LanceDB、または FAISS（ローカル完結を重視するなら軽量なものを優先） |
| LLM呼び出し | Anthropic API（Claude）を基本とし、将来的にOpenAI API・ローカルLLM（Ollama等）にも対応できる抽象化レイヤーを設ける |
| ドキュメント解析 | PDF: pypdf / pdfplumber、Markdown: 標準パーサー、テキスト: 標準I/O |
| ローカルデータ保存 | SQLite（チャット履歴・ドキュメントメタデータ管理）＋ベクトルDB（埋め込み保存） |
| パッケージング | PyInstaller等によるスタンドアロン実行ファイル化（将来的に検討） |

## 6. データ構造

### 6.1 ドキュメントインデックス
- ドキュメントメタデータ（SQLite想定）
  - `document_id`, `file_path`, `file_type`, `title`, `added_at`, `updated_at`, `index_status`
- チャンクデータ
  - `chunk_id`, `document_id`, `chunk_text`, `chunk_order`, `embedding_vector`（ベクトルDB側）, `page_number`（PDFの場合）

### 6.2 チャット履歴
- 会話（セッション）単位
  - `conversation_id`, `title`, `created_at`, `updated_at`
- メッセージ単位
  - `message_id`, `conversation_id`, `role`（user/assistant）, `content`, `timestamp`, `cited_chunk_ids`（回答の根拠となったチャンクへの参照）

### 6.3 保存形式
- アプリ内部データはユーザーのローカルディスク上（例: `~/.local_rag_chat/` 相当のディレクトリ）に保存し、外部送信はLLM API呼び出し時の必要最小限の範囲に限定する

## 7. Claude Codeのagent/skill/hookの活用案

開発練習として、以下のような対応付けを想定する。

| Claude Code機能 | アプリ内での活用イメージ |
|---|---|
| **Sub-agent** | 「検索・要約エージェント」として、ユーザーの質問をサブタスクに分解し、ベクトル検索→関連チャンク収集→要約→回答生成という一連の処理を専用エージェントに担わせる。複数ドキュメントを串刺しで調査する「リサーチエージェント」的な役割も想定 |
| **Skill** | 「ドキュメント形式変換スキル」として、PDF→テキスト変換、Markdown整形、OCR処理など、ドキュメント取り込み時の前処理を独立したスキルとして切り出す。将来的にOffice系ファイル対応を追加する際もスキル単位で拡張しやすい |
| **Hook** | 「新規ファイル追加時の自動インデックス更新」として、監視対象フォルダにファイルが追加・変更された際に自動でインデックス再構築をトリガーするフック。インデックス完了後に通知を出す、エラー時にログを残す、といった後処理フックも想定 |

これらはClaude Code自体の仕組みを模した設計であり、開発者がSub-agent/Skill/Hookの設計パターンを実践的に学ぶ場としても機能する（例えば、アプリ内の「検索・要約エージェント」の設計を、実際にClaude Codeのsub-agent定義ファイルを書く練習に転用する、など）。

## 8. 拡張ロードマップ（ステップ順）

1. **MVP**: フォルダ内ドキュメントの手動インデックス化＋チャットでの質問応答＋出典表示
2. **自動化**: フォルダ監視による自動インデックス更新（hook的な仕組みの導入）
3. **複数ワークスペース対応**: プロジェクトごとにインデックスを切り替え
4. **検索・要約の高度化**: 検索エージェントの導入、複数ステップの調査タスクへの対応
5. **対応形式の拡大**: Office系ファイル、画像OCR対応
6. **UI/UX強化**: ストリーミング表示、ハイライト表示、関連ドキュメントのグラフ可視化
7. **マルチLLM対応**: ローカルLLM（Ollama等）や他社APIへの切り替え機能
8. **配布・パッケージング**: スタンドアロン実行ファイル化、自動更新機能

## 9. 開発上の懸念点・リスク

- **検索精度の調整コスト**: チャンク分割の粒度、埋め込みモデルの選定、検索件数（top-k）の調整など、RAGの精度はパラメータ依存が大きく、試行錯誤が必要
- **PDF解析の品質**: レイアウトが複雑なPDF（表、2カラムなど）はテキスト抽出精度が低くなりやすい
- **ローカルLLM対応の技術的難易度**: ローカル完結を目指す場合、ローカルLLM実行環境（Ollama等）との連携やパフォーマンス面の検証が必要
- **大量ドキュメント時のインデックス再構築コスト**: ドキュメント数が増えると再インデックスの処理時間が増大し、UIの応答性に影響する可能性
- **APIコスト・プライバシー**: 外部LLM APIを使う場合、ドキュメント内容の一部が外部送信される点について、ユーザーへの明示と設定の柔軟性が必要
- **GUIフレームワークの学習コスト**: PySide6の非同期処理（長時間かかるインデックス処理・LLM呼び出し中のUIフリーズ回避）の実装に注意が必要
- **スコープの肥大化**: MVPの範囲を明確に保たないと、検索精度向上・対応形式拡大などで開発が長期化しやすい
